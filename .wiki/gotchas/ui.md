# UI gotchas

- **The selection clamps at a collapsed gap.** `extendSelection` stops before a gap row; once the gap is expanded the range may span both hunks (the backend accepts it). `frontend/src/lib/selection.ts`.
- **Render nothing under the selection while dragging.** Inserting the toolbar or composer under the first row shifts the rows below it, so the pointer ends up over it and the drag never extends. A mouse/pen release opens the composer directly; touch and keyboard get the toolbar, since a focused composer would pop the soft keyboard and end a tap-to-extend.
- **`pointercancel` must disarm the gutter press.** The armed flag (`dragging` in `useLineSelection`) otherwise survives a cancel, and the next unrelated pointerup anywhere opens a composer. A cancelled press keeps its selection and shows the toolbar.
- **The resolve controls sit inside the reply `<form>`, so they stay `type="button"`.** A default button submits the form and posts the draft. `ResolveControls`, rendered through `ReplyBox`'s `actions`.
- **The SSE echo of our own write is ignored.** Write responses carry the review summary; `applyReview` raises `knownRev`, so the following event has `rev <= knownRev` and triggers no refetch. Anything that bypasses `applyReview` causes one redundant refetch (harmless).
- **Verdicts are the only optimistic write** (per hunk and Accept file). Everything else waits for the server; a refused verdict reverts and toasts.
- **Accept file sends the hunk ids the UI shows as pending, never just the path.** A path alone would let the server accept hunks added by a refresh the UI hasn't loaded, or flip a reject another tab set. The server also skips any hunk that already has a verdict. A refused Accept file reverts its hunks to pending and always reloads, since the revert can clobber a per-hunk verdict set while it was in flight. `acceptFile` in `src/reviews.js`, `FileVerdict` in `frontend/src/features/diff/FileVerdict.tsx`.
- **The active verdict's tint is keyed on `aria-pressed`, not on the button variant,** so it cannot drift from the accessible state. It is the same primary (coral/orange) tint for every verdict: the hue means active, not accept/reject. It matches cc's Plan/Code ModeToggle active treatment. Ghost's dark hover rule out-specifies a plain `aria-pressed:` background (the `dark` variant adds `:is(.dark *)`), so a pressed segment needs its own dark hover shade or hovering washes the tint out; light hover needs none. Classes: `SEGMENT` in `frontend/src/features/common/segment.ts` (HunkBar's verdict group and the diff view toggle).
- **A bridge timeout or an unknown bridge code posts no result.** The prompt may have been delivered, and the backend refuses codes outside its list. The timed-out dialog's Retry warns that it could deliver twice.
- **Citations are linked from the route serialiser, never from the raw text.** Paths starting with `/` or containing `..` stay text. Parsing: [markdown.md](markdown.md).
- **The route wins on load.** A checkout named by the URL beats cc's active session, which beats the stored last checkout; only later session changes switch the checkout.
- **Spread `REVIEW_SCOPED` (`frontend/src/lib/route.ts`) into every patch that opens, leaves or deletes a review.** `navigate`/`RouteLink` merge into the current route, so a key left out (it was `round`) carries one review's view into the next: leaving a round view of A and opening B landed in B's read-only round view. A new review-scoped route key goes into `REVIEW_SCOPED`, nowhere else.
- **A past-round view hides review-level writes too** (Submit/Re-send, Refresh, Close/Reopen, Mark all read, Delete, recipient picker): they act on the current round, whatever the banner says. The commit-filter view keeps them.
- **A past-round view is a route, not state:** `round=` (range reviews only) puts `round` in the review context and makes it `readOnly`. It loses to `commit=` (the commit filter is hidden in a round view and picking a round clears `commit`), and `ReviewView` replaces a `round=` naming the current round or a later one out of the URL. Until the review loads, the open file's fetch is held: without the current round number a `round=` URL could fetch the live diff first.
- **Read-only rows have no `data-cell`.** Gutter cells carry it only when selection is enabled, so harness checks in a read-only view (closed, commit filter, past round) match rows by their cell text instead.
- **Uncommitted reviews need polling.** Working-tree edits emit no event, so the page refetches on focus and an interval; threads that vanish become session-local tombstones.
- **The file header's path keeps a flex-basis.** With only `min-w-0 flex-1` it shrinks to "a…" in the narrow desktop middle pane and the header's `flex-wrap` never kicks in; the basis makes the controls wrap instead. `FileHeader` in `frontend/src/features/diff/FileDiff.tsx`.
- **The review list scrolls inside `ReviewList`, not in its column.** In both layouts the column (`DesktopLayout`'s aside, `PhoneLayout`'s main in `frontend/src/features/layout/layouts.tsx`) has `ReviewList`'s section as its last `min-h-0 flex-1` child, so the section's inner `min-h-0 flex-1 overflow-y-auto` div is the scroller. The New review footer is a `shrink-0` sibling after that div, so it stays at the column's bottom edge whatever the list length; anything placed inside the scroller would move with the list.
- **Split pairing keeps each side's line order, so selection runs on the flat rows in both views.** `splitRows` (`frontend/src/lib/splitRows.ts`) only regroups the visible rows; `useLineSelection`, `extendSelection` and ←/→ never see pairs. A new view that reorders lines would break that.
- **Split wraps, inline scrolls.** Split columns can't scroll sideways independently without JS-synced scroll and losing row alignment, so split text cells use `whitespace-pre-wrap wrap-anywhere` and split rowgroups drop `overflow-x-auto`.
- **The split fallback observes `FileDiff`'s root, never the grid or a row.** That element's width is the pane's and does not depend on the view; observing something the view resizes could flip the view back and forth. Only the "roomy" boolean is state, so a panel drag re-renders the diff only when it crosses `SPLIT_MIN_PX`.
- **Collapse is adjusted during render, not in an effect** (`useCollapse`). An effect commits one frame with a just-accepted hunk collapsed, which unmounts a Composer under it and loses the draft.
- **`keepOpen` reads the previous render's selection through `selRef`** (`FileDiff`): collapse must be known before `useLineSelection` gets the visible rows. That is correct only because a settle (a verdict change) never changes the selection in the same render. On a file (re)load nothing consults `keepOpen`: what is settled then starts collapsed.
- **Every inline thread renders through `SettledThread`, and a collapsed card is `hidden`, not unmounted.** Same component and position whether open or resolved, so a reply draft survives Resolve and the collapse after it. An open thread whose hunk gets accepted moves under the hunk summary (a different parent), which does remount it.
- **The thread column's width is clamped on render, never written back** (`useResizablePanel`): a narrower window narrows the panel and widening it restores the stored width. A cancelled handle drag reverts and stores nothing (the same disarm rule as the gutter).
- **happy-dom has no layout.** The thread column → diff pane → split fallback link is proven only in `golden.mjs`; the unit tests pin each half (`installResizeObserver` delivers widths by hand). Row geometry, drag across real rows, sticky headers and overflow are checked in the Playwright harness, not in unit tests. A UI change that moves elements under the pointer is only caught there.
- **RTL `waitFor` hangs under vitest fake timers;** use `vi.waitFor`. `userEvent.setup()` replaces `navigator.clipboard`, so spy on it after `setup()`.
- **Rebuild `frontend/dist` (`npm run prepare`) before running the harness;** the server serves the built bundle.
