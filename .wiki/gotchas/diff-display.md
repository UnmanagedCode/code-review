# Diff display: highlighting and the Diff options

- **Ignore whitespace and Context lines are display-only, never git flags.** A hunk id hashes its path and +/- lines (`assignIds` / `changedKey` in `src/diff.js`): a larger `-U` merges neighbouring hunks and `-w` splits or drops them, both giving new ids that `setVerdict` / `acceptFile` refuse (`HUNK_UNKNOWN`) and a refresh drops. `get_hunk`'s line lookup, `annotate {hunk}`, `hunkFor`, the snapshot cache key and the uncommitted fingerprint also assume `DIFF_FLAGS`'s `-U3`. The client mirrors it as `GIT_CONTEXT_LINES` (`frontend/src/lib/gitContext.ts`), pinned by `tests/contextLines.test.js`.
- **`useFileDiff` builds rows from display copies of the hunks; `file.hunks` stay git's.** A copy (`{...h, lines, …}`) keeps `id`, `header` and `verdict`, so `HunkBar` posts the original id; the hunk row carries the copy's `lines`, keeping `collapseRows`' rule that each header is followed by exactly its `hunk.lines`. `FileDiff`'s `forced` / `keepOpen` read `file.hunks`: they test line numbers, which the transforms keep.
- **Trim, then fold whitespace.** `trimContext` works on git's real context, and a gap must hold the same text on both sides at a fixed offset (`gapSpans`); a folded row (old text ≠ new text) never lands in a gap.
- **`trimContext`'s `keepTail` is false until `total` is known.** Without a total there is no trailing gap, so the last hunk's trailing context would vanish instead of moving into a gap. A side left with no lines takes git's `-U0` start (the line before), so `first` / `last` in `diffRows.ts` stay exact.
- **Gap math uses the display hunks.** `expand`, `expandTo`, `reveal` and the gap spans all run on the same hunks `buildRows` gets; gap keys are the same as git's (`pre`, `after:<id>`), sizes are not.
- **Effective expansion = per edge max(user, baseline), where the baseline shown is min(wanted, fetched).** Raising the context waits for the baseline lines; lowering applies at once. User and `reveal` expansions live apart in `expansions`, so lowering the context never closes a gap opened for a thread. `reveal` stores only what a target needs over the user's own expansion, and `FileDiff`'s `revealKey` includes both options plus the selection as a target.
- **A folded row is one context row with both numbers.** Every old and every new number keeps exactly one row, in order, so thread keys (`side:endLine`), rails, selection and the composer anchor still find their lines; in split it is a context pair, so its old half shows the new text.
- **Whitespace-only hunks collapse through `settled`**, like accepted ones, in every view while the toggle is on; turning it off removes them from `settled`, which expands them (`useCollapse`). One holding an open thread never enters `settled`: the collapse is automatic, not a human verdict, so it must not hide a conversation.
- **Word diff has a per-decoration budget, not just per-line caps.** `decorateRows` runs over the whole file's rows on every expand, so a large rewrite (tens of thousands of pairs) blocked the main thread for seconds. `WORD_DIFF_MAX_TOTAL_CELLS` bounds the total, charged by `wordDiffCells`, which includes a fixed setup per pair so many tiny pairs count too. Pairs past `WORD_DIFF_MAX_TOKENS` are still charged (their tokenizing), so a file full of them drains the budget too; only the length-capped path is free.
- **Prism is data only.** `prismManual.ts` must be imported before prismjs (`lib/highlight/prism.ts`'s first import): Prism reads `manual` when it evaluates, and otherwise rewrites every `language-*` element's markup on DOMContentLoaded. Only `Prism.tokenize` is called; `highlightLines` flattens the tree to `{ text, cls }` with `cls` only from `TOKEN_CLASS`, and `CodeLine` renders React text. The chunk loads lazily from `useTokenizer`.
- **Decorations are keyed by `DiffLine` object**, computed on the hook's full `rows` (before collapse), so collapse, selection and view flips never re-tokenize, and inline rows and both split halves share one lookup. Highlighting sees only those rows: a construct opened in collapsed context can be mis-coloured.
- **Token colours are plugin properties, not palette tokens.** `--cr-token-*` in `index.css`'s own `:root` / `.dark` mix a palette hue toward `--foreground` in oklab (oklch would rotate the hue). The palette's hue tokens are mid-lightness for badges and tints and miss 4.5:1 as light-theme text; the binding case is a token under word emphasis on a selected deleted line. golden step 16 measures every token on each tint.
- **Highlighting cost is capped per language, because Prism goes quadratic.** Lines of unterminated literals (`"`, `'`, `/*`, `` ` ``, `<!--` left open) make the greedy patterns rescan to the end of the side from each start: at the global 1 MB cap (same bench and machine) JS took 34 s, TS 36 s, JSX 43 s, C# 25 s, Java 19 s, Go 12 s, JSON 6.8 s, Python 5.3 s, SQL 2.5 s, Ruby 0.9 s, and CSS, TSX, Bash, C, C++, PHP and Markdown ran past 150 s. `HIGHLIGHT_MAX_SIDE_CHARS_BY_LANG` caps each side (larger renders plain; word emphasis still applies). A side is the shown lines of one side, not the file. A worker tokenizer that would let the caps rise is a separate follow-up.
- **Measured worst case per side at the caps** (`harness/bench/highlight.mjs`, Node 24.18 on an Intel Core Ultra 7 265H, one process per language, worst first (cold) run over two passes, ms): markup 72 · css 66 · javascript 69 · jsx 69 · typescript 58 · tsx 68 · json 39 · bash 98 · python 92 · go 55 · rust 53 · java 51 · c 55 · cpp 38 · csharp 24 · ruby 68 · php 29 · yaml 80 · markdown 76 · sql 42 · diff 13. Measured in one long process instead, the same caps read up to 2× higher (GC), which is why the bench isolates languages.
- **`decorateRows` reuses a side whose joined text is unchanged** (a small cache keyed on text, language and tokenizer), so uncommitted polling and a toggle that leaves a side alone don't re-tokenize it. Any change to a side's shown lines (a gap expand, a context change) re-tokenizes that side, within its cap.
