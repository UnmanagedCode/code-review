# cc metadata gotchas

The plugin uses the cc GET routes in `src/cc.js` and `POST /api/exec` (`src/exec.js`) for every git command.

- `GET /api/projects/:name/location` → `{name, system, remoteId, path}`, read from the project's config (no command runs). `system` is always set; `remoteId` `null` means the provider's default target (always `null` on `local`, where sending one is refused). 404 **with** `code: PROJECT_UNKNOWN` is an unknown project; a 404 without it is a cc that lacks the route, `CONDUCTOR_UNAVAILABLE` (no fallback to the list).
- `GET /api/projects` → `{name, path, system, remoteId}`, only for the picker (`GET /projects`): cc runs several git commands per project (plus one per worktree) to build it, all projects at once, each a `docker exec` on a docker System, so nothing on a review request may ask it. `.conduct` is not listed.
- `GET /api/projects/:name/worktrees` → `{worktreeName, worktreePath, branch, baseBranch, baseSha, baseWorktree?}`. No `baseWorktree` means forked from the main checkout; the fork-point chain follows `baseWorktree` (cycle-guarded).
- `GET /api/instances` → `{sessionId, project, status, title, displayLabel?, conducted, worktree, ownerSessionId?}`. Live = `status` not `exited`/`crashed`. The conductor is the session whose `project` is `.conduct`.
- **Session labels come from cc's `displayLabel` and are never re-derived here**: cc's rule (`sessionLabel`, with `readablePrompt`'s prompt parsers) gives `(new session)` for an untitled, unprompted session, so several sessions can share a label: the recipient selects suffix colliding labels with the id prefix (`sessionOptions` in `frontend/src/lib/sessionOptions.ts`). `sessions()` in `src/checkouts.js` is the only reader: without the field (an older cc) it falls back to `title`, then each UI site to the session id.
- **`ownerSessionId` and `GET /api/conductors/projects` define a session's places** (`sessionPlaces` in `src/checkouts.js`, mirroring cc's `conductorChips`, so both views agree). `ownerSessionId` is the *root* owner of the spawn chain and is set only on live conducted instances; the history route is keyed by root session id and `sessionPlaces` re-sorts it as cc does (`lastSpawnAt` (an ISO string, so compared as a string) newest first, then project name). A history entry with no recorded worktree means a main-checkout worker, so it sets `main`. A cc too old to serve the history route (404) degrades to the live places with a logged warning; only `/api/instances` failing is `CONDUCTOR_UNAVAILABLE`.
- **The `sessionIds` lists on other cc routes are not liveness-filtered**; never use them for liveness.
- **cc stores no session role.** Author/reviewer/conductor is derived per review (`roleOf` in `src/context.js`) and frozen on each message.
- Any failure or timeout of a GET route is `CONDUCTOR_UNAVAILABLE`, except the spawn-history route's inside `sessionPlaces` (logged, degraded); their per-attempt timeout is `CODE_REVIEW_CC_TIMEOUT_MS` (default `DEFAULT_TIMEOUT_MS`). Exec has its own, `CODE_REVIEW_GIT_TIMEOUT_MS`.
- **Retries live in `ccFetch` (`src/ccFetch.js`); rules in `docs/protocol.md`.** Only transport failures are retried, never an HTTP answer. Exec retries only when the call site passes `readOnly`, which `git.js` sets through `read`/`readSh`. Gotcha: `SCAN` and `FINISH` are *not* read-only (`git diff <commit>` rewrites the index it is given, and a repeated `SCAN` after a reset that actually ran would make a second dir), so neither retries; `PROBE` and `OLD_LINE_COUNTS` are and do.
- **The operator log is a file, not stderr.** cc keeps a plugin's output only in an in-memory buffer shown as a crash tail, and never recaptures an adopted child's; `logEvent` (`src/opsLog.js`) therefore writes `<store>/logs/cc.log` (see `docs/protocol.md`).
- **Exec refusals are mapped in one place** (`exec` in `src/exec.js`; table in `docs/protocol.md`): cc's resolution codes → `SYSTEM_UNREACHABLE`, `EXEC_TIMEOUT` → `GIT_TIMEOUT`, `EXEC_OUTPUT_TOO_LARGE` → `DIFF_TOO_LARGE`, `EXEC_SPAWN_FAILED` → `GIT_UNAVAILABLE`; anything else (`INVALID_ARGUMENT`…) is code-review's own bug and a 500.
- **A cc older than `/api/exec` answers 404 with no `code`**: mapped to `CONDUCTOR_UNAVAILABLE` naming the route, so "restart cc after updating it" is the visible fix. A 404 *with* a code is a real refusal.
- **`TEMP_UNUSABLE`** (a bad `TMPDIR` on the target) degrades like the unreachable codes on the snapshot path, but is not in `UNREACHABLE`: the existence probe and `statusOf` need no temp dir.
- **"Unreachable" is never "gone":** an `UNREACHABLE` code (`src/exec.js`) from the existence probe or a snapshot becomes `snapshotError`, with `checkoutGone: false`.
- The bridge's send-failure codes are stored verbatim on a submission (list in `docs/protocol.md`).
