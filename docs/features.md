# Features

What the UI and agents can do through the backend. Wire formats are in [protocol.md](protocol.md); internals in [architecture.md](architecture.md).

## Reviews and targets

A **review** is a persisted discussion about one checkout (a project's main checkout or one of its worktrees). Opening the same open target again returns the existing review unchanged (`reused: true`): its recipient and author stay.

| Kind | Reviews | Old side | New side | Verdicts | Refresh |
|---|---|---|---|---|---|
| `range` | `base...HEAD`: the checkout's own commits | merge-base of `base` and HEAD | HEAD | yes | yes |
| `commit` | one commit (`sha`, default HEAD) | its first parent (empty tree for a root commit) | the commit | yes | refused `IMMUTABLE_TARGET` |
| `uncommitted` | working tree vs HEAD: staged, unstaged and untracked (not ignored) files | HEAD | the live working tree | none (`NO_VERDICTS`) | new round only when the diff changed |

- **Range base.** Defaults to the checkout's own fork point; a main checkout must name one (`BASE_REQUIRED`). A branch name is re-resolved through merge-base on every refresh, so after `sync_worktree` the range still shows only the checkout's own work; a sha base stays fixed. The UI offers the fork-point chain (subtask → feature → main) and any ancestor commit.
- **Committed history only.** Range and commit reviews never show uncommitted edits; the review carries a `dirty` flag instead.
- **Checkout gone** (worktree merged or deleted, project removed): range and commit reviews stay readable through the main checkout's objects; threads, replies and verdicts keep working; refresh is refused `CHECKOUT_GONE`. An uncommitted review lists its threads but has no diff.
- **Projects on a System.** A project cc places on another System (a container, a remote host) is reviewed like a local one: every git command and working-tree read runs on that System through cc's `POST /api/exec`. The project picker lists every cc project.
- **System down.** While a project's System cannot be reached (or git there times out or cannot start), its reviews stay in the list, marked with the reason (`snapshotError` `SYSTEM_UNREACHABLE`, `GIT_TIMEOUT` or `GIT_UNAVAILABLE`, never "checkout gone"); threads and replies stay readable, an uncommitted review's threads are left as they were, and opening, refreshing, the diff and the checkout picker are refused with that code until it answers again.
- **Close / reopen / delete.** A closed review refuses content writes (`REVIEW_CLOSED`). Delete is a human-only hard delete. Nothing is removed automatically.

## Verdicts and hunks

- Each hunk carries `pending` (default), `accepted` or `rejected`. Only the human sets them; no MCP tool can.
- A hunk id hashes its file path and its added/removed lines, not line numbers or context. An edit elsewhere keeps the verdict; any change to the hunk's own lines resets it to pending.
- Binary files, pure renames, mode-only changes, empty files and over-size untracked files get one file-level hunk, so every change can carry a verdict. They accept no line anchors (`BINARY_FILE`), but take file anchors.
- Renaming a file gives all its hunks new ids (the path is part of the hash).
- **Accept file** accepts the listed pending hunks of one file in one write, each recorded exactly like a per-hunk accept. Hunks that already have a verdict (rejected ones included) keep it. The request names hunk ids, so a hunk added since the UI loaded stays pending, and an id that left the round refuses the whole request. There is no whole-file reject or undo; per-hunk Pending clears.

## Groups (guided review)

A **group** is a set of hunks, possibly across files, with a title and a markdown description. The human walks a range or commit review as an ordered list of groups, gives each one verdict and comments on it as a whole. Uncommitted reviews have no groups (`NO_GROUPS`).

- **Who makes them.** An agent calls `propose_groups` (the author on its own initiative, or any session when asked). The human presses **Guide me** to ask the recipient for them (see Submitting a round). A proposal sets the round's whole list, in reading order; it never writes a verdict.
- **Membership.** A hunk may sit in several groups. Hunks in no group are the ungrouped bucket, listed with the review so nothing goes unreviewed.
- **Group verdicts.** Accept group, Reject group and Clear (reopen, which writes Pending) each write the group's own verdict and then its hunks:
  - **Accept** accepts each hunk whose every group is accepted, whatever its verdict was; other hunks are untouched.
  - **Reject** rejects every hunk of the group.
  - **Pending** on a group with a verdict sets the group and its hunks pending, except a hunk another rejected group holds (it stays rejected). Pending on a group that is already pending writes nothing, whatever its hunks' verdicts; an accepted or rejected verdict applied again to a group that already has it re-runs its hunk writes.
  - A group action never changes another group's verdict, so the outcome does not depend on the order of actions.
- **Direct hunk verdicts win.** A per-hunk verdict (and Accept file) clears, to pending, the verdict of every group holding that hunk whose verdict differs from the new hunk verdict, and writes no other hunk. Accepting a hunk directly while its group is pending changes no group. The response lists the cleared ids (`clearedGroups`).
- **Invariant:** every hunk of a rejected group is rejected, on every path.
- **Re-proposal in the same round** replaces the list. A proposed group with exactly the hunks of a current group keeps its id, verdict and threads and takes the new title, description and order. Every other current group is retired: its verdict stays as history and no longer counts, its threads go `outdated` (still repliable). No hunk verdict changes.
- **Refresh** carries a group only when every one of its hunks is unchanged (same hunk ids): same id, order, text, verdict and threads (the thread's `anchor.round` advances). Other groups are retired with reason `refresh`. Hunk verdicts carry as without groups, and a refresh never accepts code: a carried accepted group can hold a hunk that is still pending (it was waiting on a dropped group); accepting the group again accepts it.
- **Guide me is offered** when the round has no groups, a refresh dropped groups since the last proposal, or a hunk a refresh added since the last proposal is in no group (even if that refresh was several rounds ago). A proposal resets the last two. The backend does not refuse Guide me when it is not offered; the flag only guides the UI.
- **Group threads.** A group can be commented on (`anchor` `group`). They count toward the review's thread counts, unread and `mergeBlockers`, but sit on no file: they are in no per-file list, past-round view or comparison. They appear in `list_threads`, the `guide.threads` of the review detail, the thread counts and unread.
- **Activity** (inbox ordering and staleness) includes groups proposed and a group verdict set or cleared.

## Threads

- **Kinds:** `comment`, `question`, `suggestion`, `finding`. A `finding` requires a `severity` (`blocker|major|minor|nit`).
- **Anchors:** a thread sits on one of five things:
  - a line range on the old or new side; lines outside any hunk (context, expanded context) are allowed;
  - a whole hunk (stored as a line range over the hunk);
  - a whole file, any file in the diff (binary and too-large ones included);
  - a group of a range or commit review (see Groups);
  - the review itself (cross-cutting issues).
- **File and review threads over time.** A file thread follows its file: through a rename on a range refresh (`moved`); when the file leaves the diff it goes `outdated` on a range review and is dropped (`THREAD_DROPPED`) on an uncommitted one, like a line thread in that file. A review thread is never moved, outdated or dropped, and keeps its creation round. A group thread follows its group: it moves to the new round with a carried group and goes `outdated` when its group is retired.
- **Resolve.** The human resolves or reopens any thread; a finding is resolved only with a disposition (`fixed` or `dismissed`). An agent's `reply` with `resolve: true` closes an open thread it opened itself; a conductor's closes any open thread an agent opened. Closing a finding needs `disposition` (`fixed` or `dismissed`), and the call is refused `INVALID_ARGUMENT` without one. Only open threads close: anything else (a user-opened thread, an already resolved one, or an outdated one) is marked as proposing resolution, so an agent never overrides a human's close; outdated threads never change status, because earlier rounds read a thread's status from its `resolution`. A reply without `resolve` never changes status.
- **Outdated.** After a refresh, a thread whose lines cannot be found becomes `outdated` (still repliable, no longer re-anchored).
- **Limits.** A message body is capped (`BODY_TOO_LARGE`). Prompts carry file paths with control characters removed.
- **Citations.** `path#L10-L20` in a message body (relative to the checkout root) is parsed; agents see the cited lines inlined at the message's round.
- **Unread.** A thread's unread count is the agent messages the human has not read; a review opened by an agent starts unseen. The human replying or marking read clears it.
- **Roles** are derived per review and frozen on each message: a caller from project `.conduct` is `conductor`; the review's stored `author`, else its recipient, is `author` on a range/commit review; every other agent is `reviewer`. The summary's `recipientRole` is `conductor` when the recipient is the conductor session that opened the review. On an uncommitted review the human is the author, so no agent is: a non-conductor agent is a `reviewer`.
- **`mergeBlockers`** = rejected hunks + open `question` threads, whatever the thread's anchor, group threads included (open questions only on uncommitted reviews).

## Rounds and refresh

- A **round** is one snapshot epoch; messages record the round they were written in.
- `refresh` on a range review pins the new HEAD (and merge-base) as round n+1: verdicts of surviving hunks are kept, the rest reset to pending; threads follow their lines (`moved`), re-anchor by surrounding context (`drifted`), or go `outdated`. An unchanged HEAD reports `unchanged` and adds no round. The report counts the groups carried and dropped (`groups: {kept, dropped}`); see Groups for the carry rule.
- `headMoved` on a range review means the checkout's HEAD differs from the pinned one: the UI's "refresh available" cue.
- **Past rounds** (range reviews only) are viewable read-only, rebuilt from the round's pinned base and head. A range refresh records each thread's previous anchor (uncommitted reviews record none):
  - each thread sits at the anchor it had in that round (its file path then, its drift flag then);
  - messages written in later rounds are hidden and counted (`laterMessages`);
  - threads opened in a later round are absent;
  - a thread outdated in a later round shows the status it had before it went outdated; one outdated by then is outdated, at its last located anchor;
  - open/resolved is otherwise the thread's current status, and there are no verdicts, no unread counts and no proposed resolutions;
  - groups and group threads are not shown.
- **Comparing rounds** (range reviews only, read-only): round A's head against round B's head, A before B.
  - **Files:** those changed between the two heads that either round reviews (`path` in round B's diff, or `oldPath ?? path` in round A's). Upstream churn merged in between stays out; a file reverted to base in B stays in. Inside a kept file every line that differs between the heads shows, upstream edits included.
  - **Threads:** each thread live in round A sits on the left (old side) at its round-A lines, as of round A (later replies hidden and counted); each thread live in round B on the right at its round-B lines, as of B. Notes say "round A L… · outdated in round k" or "… · still applies in round B" (left copies) and "round B L…" (right copies).
  - **One card per row:** when both copies of a thread fall under one row (a context line, or a deleted/added pair in split), it shows once, as its round-B copy, noted with both positions.
  - **Not in diff:** base-side threads, threads in files unchanged between the rounds, and threads on binary/too-large files are listed under the Threads tab's Not in diff filter with the reason.
  - **Inline / phone:** one combined diff. Deleted lines are round A's, added lines round B's, context lines both; a thread on a changed line shows twice (under its deleted and its added line), one on an unchanged line once.
  - Threads outdated by round A, or opened after round B, are not in the comparison (the round-A view lists the former). Groups and group threads are not compared.
- **Uncommitted anchors are volatile.** Every read and write re-locates threads in the live working tree. A pure line shift moves the thread with its lines; changed or vanished lines delete the thread, and a later reply gets `THREAD_DROPPED`. Edits elsewhere in the same hunk never touch it.

## Submitting a round

- The human's activity since the last delivered submission is composed into a prompt for the **recipient** session (`POST …/submissions`): verdict tally, groups accepted or rejected since then (a rejected group's hunks are listed under it, not again as rejected hunks), the other rejected hunks, threads with new human messages or status changes. Uncommitted reviews ask the recipient to review the changed files instead. A conductor recipient is asked to relay the round to the author (range/commit) or to brief a reviewer (uncommitted).
- **Guide me** (`POST …/guide`, range and commit reviews) composes a different submission, kind `guide`, that asks the recipient to group the round (a conductor recipient is asked to relay it to the author). It goes through the same pending → delivered path, but only delivered **round** submissions stamp `submittedAt`, set the "since" baseline and count for `NOTHING_TO_SUBMIT`. Composing either kind supersedes every undelivered submission. A delivered guide puts the turn on the agent; `propose_groups` hands it back.
- **Recap step.** Both "Submit round" and "Request review" open a recap dialog first (Guide me and Re-send do not). It shows the recipient (label · status; "Change recipient" opens the picker), then rows: hunks accepted · rejected ("sent as decided"), undecided hunks (warning, **Review them** goes to the first one), changed files (uncommitted), threads that still need you (**Answer first**), threads already sent and still waiting on the agent (not repeated; only after a delivered round), and the threads going out ("will be sent", each a link). Undecided hunks and open threads never block sending. An optional **Overall note** is kept as a draft per review and, on send, stored as a review-level thread (Review tab, History, MCP). With nothing new since the last delivered round the primary is disabled until a note is typed. "Preview the prompt" (collapsed) shows the server-rendered text for the current note. There is no Approve / Request changes control: hunk verdicts carry that. Primary: "Send to …" with a bridge, "Compose prompt" standalone (it leads to the copy dialog with Copy and Mark as sent).
- **Not reviewed yet.** The prompt's tally reads "N not reviewed yet", and a `Not reviewed yet (no verdict from the human; do not treat these as accepted)` section lists every undecided hunk (path, header, `h:id`; capped, then "… and N more"). The note appears in full under `Reviewer note [tN] (reply on that thread)`, not under the thread list. Uncommitted reviews have no verdicts and no such section.
- The prompt is stored `pending`; the UI sends it through the cc bridge and reports the outcome. `delivered` stamps the round's `submittedAt`; a failure keeps it re-sendable; composing again supersedes undelivered ones. A first submission is always allowed; later ones need new human activity (`NOTHING_TO_SUBMIT`).
- **Recipient.** An agent-opened review: the opening session. A human-opened one: the explicit session, else the single live session attached to the checkout, else none (`NO_RECIPIENT` on submit until set).
- **Author.** A conductor opening a range/commit review names the worker with `author`; the stored session takes the author role while the conductor stays recipient and relays the rounds.

## Agent surface

- **MCP tools** (`code-review__<tool>`): `open_review`, `get_review`, `list_threads`, `get_hunk`, `annotate`, `reply`, `propose_groups`, `refresh_review`. Review and thread results carry a `link` that opens them in the plugin view. Each tool answers in cc's json format (complete structured data) or text format (prose; a long cited excerpt is cut there with a note saying how to read the rest). Schemas and results: [protocol.md](protocol.md#mcp).
- **Skill** `review-dialog` (`skills/review-dialog/SKILL.md`): how an author or reviewer session works a review.
- **Conductor convention** `review-in-code-review` (`conventions/conductor-review.md`, scope `conductor`, opt-in per task): one inline line names the trigger and the skill part, invoked as `cc-conductor-code-review:review-in-code-review`; the skill opens a review on the worker's checkout naming the worker as author, has reviewer lenses post findings, closes each finding the conductor rules on with a disposition, and holds `merge_worktree` while `mergeBlockers` is above 0.

## Review UI

The plugin page. Wire calls are in [protocol.md](protocol.md); module layout in [architecture.md](architecture.md#frontend).

- **Screens.** While no review is open the side pane has two tabs, **Inbox** and **Checkout** (the default). Checkout: pick a project and worktree (CheckoutBar), list its reviews (this checkout or every checkout of the project; open, closed or all), start one (New review: range with a fork-point shortcut or any ancestor commit, one commit, or uncommitted). An empty list names its status filter: No open reviews, No closed reviews, or No reviews yet (All). A link (e.g. from code-git) can open New review prefilled with a range ending at HEAD or one commit; the human still picks the recipient and confirms, and a link that cannot be used shows why and leaves the defaults ([protocol](protocol.md#ui-routes), New review links). Inbox: every open review of every project and checkout, in triage sections. Where the page opens: [Opening the page](#review-ui). Then work a review: the side pane (header, scope line, and the Files, Threads and History tabs) beside one file's diff.
- **Opening the page.** A checkout named by the URL, or by cc's row menu, wins. Otherwise, embedded in cc: with an active session, the session's one open review (it is that review's recipient or author) opens at once, replacing the history entry; with none or several, the inbox of the session's checkout shows. Standalone, or with no session selected, the inbox shows on the last checkout used. The inbox shows (not the empty project picker) while this is decided.
- **Inbox.** Every open review of every project and checkout, in the server's order (below). Closed reviews are not listed.
  - **Sections**, in this order, each headed with its count; empty ones are left out. **Needs you** (marked with an accent bar): the human's turn and at least one reason (the chips below), most urgent first, then latest activity (ties: newer id first). **Waiting on agent**: the newest submission was delivered and the agent has not acted since. **Nothing pending**: the rest. **Stale** (collapsed until its header is opened): idle for more than `STALE_AFTER_MS` (`src/triage.js`) or checkout gone; it wins over every other section. Latest activity first inside the other sections.
  - A row shows the title (else the target label) with the age of its last activity (`12 min`, `3 h`, `2 d`), then `project · worktree` (`main checkout` for the main one) · kind · round; chips for why it is listed, most urgent first, on Needs you and Stale rows only (**N need you**, **send failed**, **send unconfirmed**, **N hunks undecided**, **N groups to decide**, **not opened**, and only when none of those applies, **unsent changes** or **never sent**; **N will be sent** stands in for the first), then **new activity** since the human last viewed the review, **sent 3 h ago** while waiting, and on stale rows **checkout gone** and **idle 30 d**; and a line naming the agent's last act (**Agent replied on a.ts#L3**, **Agent says a.ts is fixed**, **Agent opened a thread on …**, **Agent resolved …**, **Agent updated the review**), or **No reply yet** while waiting. A review whose current round stored no hunk ids (uncommitted, or stored before ids were kept) has no hunk chip; when nothing else applies it carries the **never sent** / **unsent changes** fallback. Picking a row opens that review in its own checkout (a history entry: Back returns to the inbox).
  - **Overview.** On a wide screen, with no review open on the inbox, the centre says how many reviews need you and how many threads wait on you, and **Start with "<title>"** opens the top Needs-you row; with none, "Nothing needs you right now".
  - **Whose turn:** **Waiting on agent**: the newest submission was delivered, and no agent has replied, annotated or refreshed into a new round since it was composed. Otherwise it is the human's turn: nothing submitted yet, the newest submission is pending or failed (it needs Re-send or Mark as sent), or an agent acted after it. The human's own comments, verdicts and refreshes while waiting keep it on the agent.
  - **Activity** (what orders the list and ages a row toward Stale): every message, verdict set or cleared, thread resolve or reopen, submission composed, submission result recorded, groups proposed, a group verdict set or cleared, and refresh that adds a round. Marking read, renaming, changing the recipient, closing/reopening and an unchanged refresh are not activity.
  - **Checkout gone:** a row whose project or worktree cc no longer lists sits in **Stale** with a "checkout gone" badge and a **Close** button (closes the review; it leaves the inbox). When cc cannot be reached the rows show no badge. The inbox runs no git, so it never marks a System that is down; opening the review shows that.
  - **Live updates:** any review event refetches it. A worktree cc removes with no review activity is marked on the next refetch (the next review event, or reopening the inbox).
- **Open from code-conductor.** The ⋮ menus of cc's project and worktree rows have **Show reviews** (grouped under Code Review). The project row means its main checkout. Contract: [protocol](protocol.md#ui-routes), Row menu.
  - Lands on that checkout's one open review if it has exactly one; else on the Checkout tab for that checkout, reset to This checkout / Open (empty: "No open reviews").
  - An unknown project or worktree, a missing project, or a failed request shows a toast naming it; the page stays as it was.
  - Read-only: nothing is created, and the last-used checkout is not remembered.
  - A project on a System works while the System is down: code-review runs no git for it, reading only cc's project and worktree records; the list shows the stored reviews and the CheckoutBar shows the System's error.
  - Reload and Back never repeat it (every write replaces the history entry); an open page retargets in place, without reloading. Picking a checkout or opening a review before it lands wins: the click is dropped silently, whether it would have landed or failed.
  - On a load from the menu, the page does not first follow the active session's or the last-used checkout; later session changes follow as usual.
- **Open in code-git.** Embedded in cc with the code-git plugin enabled: the review actions menu's "Open head in code-git" (the current round's head commit), an icon link on each History commit row (that commit), and an icon link in the file header (the file's history at the commit the diff's new side shows; none for a deleted file, nor for an uncommitted review's added or renamed file). Hidden standalone and without code-git. Contract: [protocol](protocol.md#ui-routes), Open in code-git.
- **Session names.** Every place that names a session (recipient picker, New review's recipient, review header, author badges, the "following" note, the submit dialog) uses cc's sidebar label for it: its title, else its first prompt, else `(new session)` for an untitled session with no prompt yet. In the two recipient selects (the picker and New review), sessions whose labels collide get ` · <first 8 characters of the id>` appended (`frontend/src/lib/sessionOptions.ts`); a unique label stays as it is. A cc that sends no label gives the session's title, else its id (its first 8 characters in author badges and the following note).
- **Review header.** Shows the recipient (a button opening the picker) and, when the review names one, a plain `Author: <session label>` text.
- **Progress strip.** In the review header, on the live review only (not in a past round or comparison): **Hunks a of n decided** with a bar and a link **k undecided →** to the overview's Hunks card, then pills for the open threads by whose move they wait on. Each pill opens the Threads tab filtered to it (`need=`, a chip "Showing: … · N" with ✕). A pill with 0 is omitted. Uncommitted reviews have no hunk part (no verdicts). While the review's diff is unreadable the pills are plain counts, not links (the filtered list could not load file and line threads).
  - **Counts** (one definition each): a = accepted + rejected hunks and n = all hunks of the current round; k = pending hunks; **N need you** = open threads in `awaiting-human` or `verify-resolution`, any anchor, never the unread count or outdated threads; **N will be sent** = `unsent`; **N waiting on agent** = `awaiting-agent`. The three sum to the open threads. The Threads tab's own badge is the unread count and is a different number.
- **Thread states.** A card shows a chip: **Needs your reply** (an agent acted last), **Will be sent** (your last act is not in a delivered round yet: a pending, failed or Guide me submission does not count), **Waiting on agent** (a delivered round holds your last act). An agent's proposal to resolve keeps its own "proposes resolution" chip and banner (the pill and overview call it "Agent says fixed — verify"). Past rounds and comparisons show no state.
- **Overview.** The centre of a live review whenever no file is open (past rounds, comparisons and the commit filter keep "Select a file"); on a phone its own screen behind the strip's **Overview** link, with Back to files, and a file opened from it returns to it. It shows the scope line, **Review next undecided hunk** (opens the first file in tree order with an undecided hunk; hidden when none is, or on uncommitted reviews), **Needs you** (the open threads awaiting you, in place order, each opening its thread), **Hunks** (decided out of all per file, range and commit reviews only), **Your threads** (**Will be sent** and **Waiting on agent**), and **What the agent did — since you last looked**.
  - **Since you last looked:** the agent's thread events (opened, replied, proposed resolving, resolved) newer than where you last viewed the review, pinned when you open it so the list stays while you read. Group proposals and agent refreshes are not listed. A last row says whether the round was sent, to whom and when. While the diff is unreadable, file- and line-anchored rows and feed items say "diff unavailable" instead of linking; review and group rows stay links.
- **Jump navigation and keyboard shortcuts.** The file header's second row steps through the review; **?** (or the header's Keyboard shortcuts button, hidden on touch devices) opens the cheat sheet. Every icon or stepper button has a tooltip naming its key.
  - **Keys** (the catalog is `SHORTCUTS` in `frontend/src/lib/shortcuts.ts`):

    | Key | Does |
    |---|---|
    | `n` / `p` | Next / previous open thread, across every file |
    | `u` | Next thread that needs you (wraps; a toast when none does) |
    | `]` / `[` | Next / previous file |
    | `j` / `k` | Next / previous hunk of the open file |
    | `a` / `x` / `0` | Accept / reject / clear the focused hunk |
    | `o` | Overview (leaves the open file; Threads and History keep their pane tab). On the Guided tab it writes `view=overview`, so the pane moves to Files, exactly as the progress strip's **Overview** link does |
    | `s` | Submit round: opens the recap, sends nothing |
    | `v` | Mark the open file viewed, or clear the mark (the header's check button): acts only with a file open on the live review |
    | `/` | Filter files: brings the Files tab forward and focuses the filter box; acts only where the tree is mounted (not on a narrow layout with a file open) |
    | `?` | Keyboard shortcuts |

  - **Never while typing.** No key acts from a text field, a native select, or inside a dialog, menu or listbox, with Ctrl, Meta or Alt held (AltGr excepted), or during IME composition. Held keys repeat only for `j` and `k`.
  - **Thread walk.** `n`/`p` walk every open thread (any anchor) in the order the overview lists them: threads that need you (**Needs your reply**, **Agent says fixed — verify**) first, then the rest, each part in place order (file tree order, old side before new, line; then group threads by step, then review threads). They stop at the ends. A thread reached from another file opens that file; the card takes keyboard focus, so Tab reaches its reply box. Stepping inside one file replaces the history entry; reaching another file pushes it, so Back returns to the previous file. After you reply, the thread leaves the needs-you part and the next `n` continues from the slot it held, however you opened it (a step, a row or card click, a link), so no needs-you thread is skipped. On a phone a step to a review thread leaves the file for the pane's Threads tab. In a past round, comparison or commit filter there is no thread stepping.
  - **File walk.** `]`/`[` and the header's ‹ › buttons follow the Files tab's tree order (directories first), ignore any filter or collapsed folder (and expand the folders of the file they reach), don't wrap, and with no file open `]` opens the first file and `[` the last. The header reads **File i of N**.
  - **Hunk walk.** `j`/`k` scroll the next or previous hunk of the open file to just under the sticky header and focus it (the focus ring marks it); Once a hunk is focused they step one hunk at a time from it (so they stop at the first and last hunk even when the page cannot scroll further); `k` from a hunk scrolled past its start goes to that start first. A hunk beyond the rendered rows widens the window to reach it. The header's **Hunk k of N** names the focused hunk while it is on screen and follows the scroll otherwise; when the focused hunk has scrolled out of view, `j`/`k` and the chevrons follow the scroll too. Binary and too-large files have no hunk stepper.
  - **Verdict keys.** `a`, `x` and `0` decide only the hunk that holds keyboard focus (after `j`/`k`, a landing, a click, or Tab); focus in a thread card does not count, so a letter meant for its reply box never decides a hunk. A key that would contradict its guided group's decided verdict is refused with a toast (change it from the hunk bar or the Guided tab); every applied key shows a toast with **Undo**. Unavailable on closed reviews, uncommitted reviews, past rounds, comparisons and the commit filter.
  - **Cheat sheet.** Lists the shortcuts that act now, by group, plus the diff grid's line-selection keys (arrows, Shift+arrows, Space/Enter, `c`, Esc). `?` and Esc close it; focus returns to where it was.
- **Layouts.** Wide (≥ `md`, 48rem): a side pane on the left (the Inbox and Checkout tabs, or the open review's pane) and the diff in the centre. Narrow (phone or a narrow docked pane): one pane per route (list → review pane → diff). On a phone the review pane shows while no file is open (on the Guided tab: the step list, or, once `step` is set, that step full screen with **Back to steps**). Picking a file, or a thread's Focus or location link, opens the diff, whose header has **Back to files** (back to the pane, on the tab it was left from; from a file opened by a step's **Open in file**, back to that step) and a **Threads** button (with the open-thread badge) that opens the pane's Threads tab. On a phone the Threads tab's This file filter is empty while the pane shows. Both layouts have the Inbox and Checkout tabs; the review header has an **Inbox** link beside **← Reviews** (on a phone, on the review pane shown while no file is open). The page follows cc's theme and has no theme control.
  - **Resizable side pane** (every wide layout, the checkout and review-list column included): drag its right edge, or focus the handle ("Resize side pane") and use → to widen, ← to narrow (16px; Shift: 64px), Home (narrowest), End (widest). The width stays between the pane's minimum and maximum and always leaves the diff its minimum while the window allows (`PANE_DEFAULT_PX`, `PANE_MIN_PX`, `PANE_MAX_PX`, `DIFF_MIN_PX` in `frontend/src/lib/paneWidth.ts`); a narrower window narrows the pane without forgetting the chosen width. Remembered in this browser (`code-review:sidePaneWidth`).
- **Diff.** Inline (unified, the default) or split, both with both line-number gutters. Split pairs each run of deletions with the additions after it side by side (the n-th deletion beside the n-th addition, the shorter side padded with empty cells), shows context on both sides, and wraps long lines; inline scrolls long lines sideways on a wide screen and, on a narrow one (a phone), wraps them too, with narrower line-number gutters, so no code is clipped. Context outside the hunks is collapsed; a gap expands 20 lines at a time or fully, and a thread whose range reaches into a gap opens enough of it (from the nearer edge) to show the thread's whole range. The first 1 500 rows render, then "Show next …". Binary and too-large files show a placeholder with their verdict bar.
- **Syntax highlighting and word emphasis.** Code is coloured by language (from the path: `languageFor` in `frontend/src/lib/highlight/index.ts`; an unknown extension is plain) once the highlighter's lazy chunk has loaded. A file side (the shown lines of one side, joined) renders plain, uncoloured, when it has a line over `HIGHLIGHT_MAX_LINE_CHARS`, more than `HIGHLIGHT_MAX_LINES` lines, or more characters than its language's cap: `HIGHLIGHT_MAX_SIDE_CHARS_BY_LANG`, else `HIGHLIGHT_MAX_SIDE_CHARS` (same file). Word emphasis still applies on a plain side. Only the lines shown are highlighted, so a construct opened in collapsed context can be mis-coloured. Within a run of deletions and additions, the n-th deleted line is paired with the n-th added line (as split pairs them) and the changed words of each pair get a tinted background; a line past `WORD_DIFF_MAX_CHARS` or `WORD_DIFF_MAX_TOKENS` (`frontend/src/lib/wordDiff.ts`) gets none, and once a file's pairs (in row order) have used `WORD_DIFF_MAX_TOTAL_CELLS` of word-diff work, the rest get none. Token colours (keyword, string, number, function, tag, comment) are distinct hues in both themes, at least 4.5:1 on every row tint and 3:1 under word emphasis; comments have their own colour and are italic.
- **Diff options.** The **Options** button (sliders icon) in a text diff's file header, in every view (read-only ones too). Display-only: hunk ids, verdicts and thread anchors never change, and a change re-opens any gap that would hide a thread's range, the `lines=` target or the selection. Its name lists the settings that differ from the default (a dot marks them). Remembered in this browser (`code-review:ignoreWhitespace`, `code-review:diffContext`).
  - **Ignore whitespace** (off by default): a deleted and an added line of one run that differ only in whitespace (git `-w`) show as one context row carrying both line numbers and the new text; word emphasis ignores whitespace. A hunk with no other change, and no open thread on its lines, collapses to a summary badged "whitespace only" that keeps its id and verdict, still counts as pending and expands to its verdict bar (see Settled items). Added or removed blank lines, and an end-of-file newline change, still count. Files whose only change is whitespace stay listed with their counts; the `@@` headers keep git's counts.
  - **Context lines** (`CONTEXT_CHOICES` in `frontend/src/state/diffPrefs.ts`, default git's 3): more opens that many lines beside each hunk (the gaps' edges, read like "Show 20"); fewer moves each hunk's leading and trailing context into the gaps beside it, while context between two changes of one hunk stays (verdicts are per hunk). In the commit filter (no gap reads) values above 3 act as 3.
- **Diff view.** The Inline / Split toggle sits in the file header of a text diff and is remembered in this browser (`code-review:diffView`). Split needs the wide layout and a diff pane at least `SPLIT_MIN_PX` (36rem, `frontend/src/features/diff/useDiffView.ts`) wide, and once shown it stays until the pane is narrower than `SPLIT_MIN_PX − SPLIT_EXIT_SLACK_PX`; below that the diff is inline, the toggle is hidden and the stored choice is kept. The view follows the diff pane's width live (window, cc's dock pane, or the side pane's width). Phones are always inline.
- **Settled items.** An accepted hunk and a resolved thread show as a one-line summary (the hunk's `@@` header with "accepted"; the thread's kind, the first line of its first message as plain text, its range (as on its card), "resolved" and its disposition; on one line, except in a narrow pane such as a phone, where range and badges wrap below the preview); click to expand, and the chevron collapses again. Expanding only changes the view and is forgotten on reload or file switch. Un-accepting or reopening expands the item; settling it again collapses it. A collapsed hunk has no verdict bar (expand it to change the verdict); its open threads stay listed under its summary. A hunk holding the current selection offers no collapse control. Navigating to a thread (`thread=`) shows it expanded, even when resolved. If it gets resolved while focused (by you or an agent), it collapses like any other. Every hunk holding the focused thread's range and every hunk holding the `lines=` range are always expanded. Accepting a hunk that holds the current selection keeps it expanded. No collapsing of accepted hunks in uncommitted reviews, the commit filter or past rounds (no verdicts there; resolved threads still collapse), nor in the Threads tab. While Ignore whitespace is on, a whitespace-only hunk collapses in every view, under the same rules (forced, focused-thread and selection hunks stay open), except one holding an open thread, which stays expanded; turning it off expands it.
- **Drafts.** An unsent reply (per thread) or new comment (per anchor: range, hunk, file or the review, with its kind and severity) is kept for the browser session, so it survives its form moving or remounting: a hunk collapsing over the thread, a view flip, closing and reopening the same range. Sending clears it; Cancel discards a new comment's draft. A reload loses drafts.
- **Comment on file.** An icon button in the file header (live, writable view only: not read-only, past-round, comparison or commit filter views, nor a closed review), binary and too-large files included. It opens a composer ("This file") first in the **file-threads block** between the header and the diff, scrolled into view below the header however far the diff was scrolled; the block also lists the file's file threads (resolved ones collapse to a summary, as in the diff; in a comparison a thread's two copies show once, noting both rounds).
- **Per-hunk bar.** An undecided hunk shows a muted "undecided" and a two-segment **Accept | Reject** with neither drawn as chosen; a decided hunk shows a chip (**✓ Accepted** on a green tint, **✗ Rejected** on a red one, the label in the neutral foreground colour) and a **Clear** link that sets it undecided. Both write the same verdict as the `a`, `x` and `0` keys. "Comment on hunk" (anchors the whole hunk) sits beside it. Uncommitted reviews have no verdict controls; file-level hunks (binary, rename, mode) take a verdict but no comment; the commit-filter view has no bar.
- **File path.** The file header shows the open file's path with the base name kept whole. When the path doesn't fit, the directory gives way from the left (`…/files/Name.tsx`), then the name from the left (its extension stays visible). Hovering shows the full path, and selecting the text copies it. The file's status shows as the tree's letter (M/A/D/R), whose tooltip names it.
- **File verdict.** The file header shows "a/n accepted" ("· r rejected" when any) and **Accept file**: disabled when nothing is pending or the review is closed, replaced by "All accepted" once every hunk is accepted, absent on uncommitted reviews and in the commit-filter view. Optimistic like per-hunk verdicts.
- **Selecting lines.** A selection covers one side's numbers only and stops at collapsed context or a collapsed hunk; expanding the gap lets it span two hunks. In split the left column selects the old side and the right column the new side; keyboard behaviour is the same in both views. No selection on binary or too-large files, closed reviews or the commit-filter view.
  - **Hover cue and hint (mouse/pen):** hovering, or keyboard-focusing, a line number you can comment on shows a `+` chip over it (decorative; it never intercepts the press or drag), and a one-line hint "Click or drag line numbers to comment" sits between the file header and the grid (outside the sticky header, so it adds no header height; truncated only when the grid is narrower than the text). The gutter is 3rem wide (2.25rem on the wrapped narrow layout) for files whose line numbers have up to three digits; a file with a wider number gets a gutter that fits its widest number on either side (`lib/gutter.ts`, `--gutter-w` on the grid), fixed for the file, so the `+` never covers a digit. Neither is shown on touch (`(hover: none)`), in read-only views (closed review, past round, comparison, commit filter), on binary or too-large files, or on Guided step hunks.
  - **Mouse/pen:** drag over one side's gutter, shift+click to extend, a plain click restarts. Releasing a press on a gutter (drag, click or shift+click) opens the comment composer for that range, Message focused. Selecting code text never opens it, nor does a press the browser cancels.
  - **Touch:** tap a line, tap another to extend, tap an endpoint to clear.
  - **Keyboard:** the diff is one tab stop; arrows move, ←/→ switch side, Shift+↑/↓ extend, Space/Enter select, `c` comments, Esc clears.
  - **Toolbar:** touch and keyboard selections (and a cancelled mouse press) show a toolbar under the selection ("L10–L14 (new)", Comment / Clear) instead of the composer.
- **Threads.** Shown under their end line (in split, full width under the row holding it); several stack in id order, old side first. Each card has kind and severity badges, status, its range (`L3–L5 (new)`; not on outdated or dropped cards, nor in a comparison, where the comparison note names each round's lines), disposition, a "re-anchored by context" chip for drifted anchors, a "proposes resolution" chip and banner, author badges ("You", or the role plus the session label), a reply box and resolve controls (a finding resolves "as fixed" or "as dismissed"). Reply and the resolve/reopen controls form one right-aligned action row, Reply last. Outdated threads are listed only in the panel's Outdated tab, labelled with their old lines and round, with a reply box and no status controls; their location link (`file · L10–L14 (new)`, the last located range their "was …" line names) and Focus open comparison `R..R+1` (R = the last round the thread was located in) at their old lines, where the thread sits in place (a base-side thread opens round view R instead). When the thread's file is not in that comparison (unchanged between the two rounds, or renamed), a read-only excerpt of round R's lines shows instead; a renamed file is not opened under its new path. In a comparison, Focus on a thread it does not place ("Not in diff") only focuses its card. Focus on a thread in another file opens that file at the thread.
- **Thread ranges.** Every line a thread spans carries a range rail: a thin vertical bar in the line-number gutter of the thread's side (inline: the old or new gutter; split: the left or right half), with rounded caps on its first and last line. Rails never tint the row, so added, deleted, context, selected and cited lines keep their colours. Ranges that overlap or touch get separate lanes, up to `MAX_LANES` (`frontend/src/lib/ranges.ts`); deeper overlaps share the last lane. Open and resolved threads look the same. The focused thread (`thread=`) has a wider rail in the active colour, its line numbers take the foreground colour, and its hunks stay expanded. In forced-colours mode (Windows High Contrast) rails use system colours: `CanvasText`, and `Highlight` for the focused thread, whose rail is also twice as wide there. The gutter cell's accessible name lists the ranges it sits in (`new line 4 · in question thread L3–L5 (new)`). Outdated threads, dropped threads, comparison threads with no place in the diff, and lines inside a collapsed hunk carry no rail. In a comparison a round-A copy marks the old side and a round-B copy the new side.
- **File tree.** One line per file, in tree order (directories first, then name): a **viewed checkbox** (live review, writable), the status letter, the name (muted once viewed; it truncates before anything else does), the file's **+/− lines** (green/red, none for a file with no line changes; 10,000 or more reads compacted, `123k`, `1.2M`, with the exact numbers in its accessible name), the file's verdicts as one square per hunk (accepted, rejected, undecided; a proportional bar past eight hunks; "N hunks" on an uncommitted review or a past view) and the open-thread count (in the primary colour when the file has a thread waiting on you). Indent stops growing past a fixed depth. Hovering a row shows the full path (`old → new` for a rename). A legend sits under the tree.
  - **Folders collapse.** A folder row is a chevron button (Tab, Enter or Space); folders start expanded. Collapsed, the row shows `N files` and their summed +/−, counting only the files the filter keeps. The state is kept per review for the page session (a phone's round trip through a file keeps it; a reload resets it). Opening a file by any route (`]`/`[`, a thread, the overview, a link) expands the folders above it once; you can collapse them again.
  - **Viewed marks** belong to the review and survive reloads. A mark is the file's hunk ids when it was set, so any change to a hunk's own lines, a new hunk or a rename clears it (as it resets a verdict); a refresh that leaves the file alone keeps it. The write is optimistic like a verdict; a refused one (the file changed meanwhile) reverts and reloads. Past rounds, comparisons and the commit filter show no marks.
  - **Filter.** A box ("Filter files", `/`) matches a case-insensitive substring of the path; **Needs me N** (files with an open thread waiting on you) and **Undecided N** (files with a pending hunk; not on uncommitted reviews) toggle, and keep a file matching either when both are on; the text applies on top. Beside them: "X of Y viewed". While filtering: "Showing a of b files · Clear filter". The filter is kept per review while the page is open, so it survives a phone's file round trip. It never changes the order, and the file walk ignores it.
- **Pane tabs.** The review pane has the header, the banners (round view, comparison, closed, checkout gone), the refresh controls and a scope line on top, then the tabs **Files** (the file tree; a refused round view or comparison shows the refusal here), **Guided** (see below; only where it applies), **Threads** (with the open-thread count of what is shown as a badge, none at zero) and **History** (range reviews only). The tab is the route's `view` (absent = the review's default tab) and survives every file, thread and scope navigation; switching tabs, Files included (`view=files`), replaces the history entry, so Back skips tab switches. **Default tab:** a live review with proposed groups opens on **Guided** unless a file is routed; otherwise Files. It is decided once, at the review's first load in a visit, and derived: it is never written to the URL (so a pending session or menu landing is not cancelled). Groups arriving later do not switch the tab. On a wide layout the Guided tab with no file open shows its step (step 1 when none is routed) in the centre, whether it was chosen or the default; the **Overview** link in the progress strip and `o` reach the overview.

  | Situation | Tab |
  | --- | --- |
  | `view=` in the URL (a deep link or a saved choice) | The URL wins |
  | `file=` deep link, no `view` | Files for the whole visit |
  | Review/group thread links | Their own `view=threads` / `view=guided` |
  | MCP review links, Inbox and Checkout rows, "Start with", the session landing | Guided when the review has groups |
  | Past round, comparison or commit filter at first load | Files for the visit |
  | Groups arrive or vanish after the first load | No switch |

  Inactive tabs keep their state (the thread filter's choice, the status and owner selects).
  - **Scope line:** what the diff and threads show: `Round n · <head>`, `Round n · commit <sha>` (commit filter), `Round k · <head> · read-only` (past round), `Round A → B · read-only` (comparison), `Commit <sha>` (commit review), `Round n · working tree` (uncommitted). On range reviews it is a button that opens History and focuses its tab.
- **Guided tab** (see [Groups](#groups-guided-review)). Shown on range and commit reviews whose guide has groups or offers Guide me, and the default tab when it has groups; never on uncommitted reviews, and not in a past round, a comparison or the commit filter, where `view=guided` shows Files (the URL is left alone). Read-only on a closed review.
  - **In the pane:** **Guide me** with its reason (when offered and not read-only: "No groups yet — ask <recipient> to group this round", "A refresh dropped N groups since the last proposal", "N new hunks are in no group"); a progress line "Step i of n · a accepted · r rejected"; the steps in reading order (number, title, verdict badge, unread badge; the current one is `aria-current="step"`); then **Retired groups** (title, round and reason). **Other changes** is the last step, only when some hunk is in no group, and shows "d/m decided" instead of a verdict. No groups: "No groups for this round".
  - **Step view** (wide: the centre; phone: the whole screen with **Back to steps**): a sticky header (Step i of n, the title, Previous step / Next step, and the group verdict, none on Other changes, disabled on a closed review: "undecided · Accept group | Reject group", or a chip (✓ Accepted / ✗ Rejected) with **Clear**, plus **Accept group again** on an accepted group that still holds pending hunks). After the server confirms Accept group or Reject group, focus moves to **Next step** (on the last step it stays on the verdict control); the step never advances on its own, and a refusal leaves focus on the control, a one-line note, the description, the group's threads with **Comment on group** (not in read-only), then the group's hunks under one collapsible bar per file (see **Hunks**). With no `step` the first step shows; an unknown `step` is replaced out of the URL.
  - **Verdicts.** A group verdict is optimistic on the group's own control only; its hunks change when the response lists them (the rules live in `src/grouping.js`). A refusal reverts the control and toasts. **Accept group again** re-sends an accepted verdict (it re-runs the hunk writes). Hunk verdicts and the groups they clear come from the server's response only.
  - **Notes** (the group verdict disagrees with its hunks): "Set back to pending: you changed the verdict of one of its hunks." after a hunk verdict of yours cleared the group (session-local; shown while the group is pending), or "n hunks still pending — Accept group again to accept them." on an accepted group holding pending hunks (a carried group). No toast.
  - **File bars.** Each file is a bar pinned under the step header: a button showing the path, the hunk count, "n pending" or "decided", and the open line threads, with the file's hunks below. The first time a step opens in a page session its first file is open and the rest are collapsed; your open/closed choice is kept per review and step until reload (so Back from **Open in file** finds the file open). A `thread=` naming a line thread in the step opens its file. On Other changes, which has no group verdict, a bar's pending count points at hunks still to decide inside it.
  - **Hunks** use the diff's own rows (verdict bar, **Comment on hunk**, line threads and rails, accepted-hunk collapse), inline only: no gap expansion, line selection, split view or Diff options. **Open in file** on each hunk opens that file at that hunk's lines (the new side; the old side for a pure deletion), keeping the Guided tab and step. A hunk that left the file shows "This hunk is no longer in the file".
  - **Retired view.** A retired group opens from the pane (`step=<id>`): its title, "Retired in round N (refresh | re-proposal) — its verdict no longer counts", and its outdated, repliable threads.
  - **Text.** Titles are plain text. Descriptions go through the message markdown; they carry no server-parsed citations, so `path#L…` in a description shows as text, not a link.
- **Thread filter** (inside the Threads tab, its own tab list "Thread filter"; it scrolls sideways when the pane is too narrow, and a tab that takes focus is scrolled into view). The Threads tab opens on **All**. Threads are compact rows, two lines each: the state chip (**Needs your reply**, **Agent says fixed — verify**, **Will be sent**, **Waiting on agent**; a resolved or outdated thread shows its status), the place (`a.ts#L3–L5`, the file's name, `review`, or the group's title; the full place is the tooltip), the kind and the age of the last message; then a one-line preview with an unread dot. A row is one button that opens the thread in place; **the routed thread opens as its full card** (reply, resolve, read mark), and shows a loading line while its file loads. This file; All (open threads in collapsible sections **Needs you**, **Will be sent** and **Waiting on agent**; the status filter Open / Resolved / All adds a **Resolved** section; owner filter — all/user/agents, by who opened the thread; "Next unread"; review threads and the live round's group threads included); Outdated (with the outdated group threads); Review (the review threads, and **New review thread** outside read-only views); in a past round or comparison every tab shows loading, then the load error with Retry, until that view has loaded; Dropped (uncommitted only). A comparison keeps cards and defaults to This file.
  - **Counts agree.** Under the default filters (Open, all owners, no `need`) the **All** count, the Threads tab's badge, the review's open threads and the sum of the strip's pills are one number: the open threads of any anchor. Each tab counts what it lists, after the status, owner and `need` filters; with `need=` only that section shows, and its chip's number is the number of rows.
  - **Where the data comes from.** The live review's open threads come from the review detail (`openThreads`), so the default list reads no file diff. Only the Resolved list, or a past round, reads each file's diff (the thread index), and only while the Threads tab is the one showing.
  - A `thread=` naming a review thread selects the Review tab. A review thread's row (and "Next unread" on one) routes to `view=threads` and the thread, keeping the open file; a file thread's opens its file with no side or lines (an outdated one: the round view it last sat in). A group thread's row and "Next unread" open its Guided step with the thread focused (`view=guided`, `step`, `thread`), leaving the open file and any past view. A row for another file's thread opens the file and focuses the thread (`file`, `side`, `thread`; any `lines=` is cleared), staying on the Threads tab: the range rail marks its lines. The `lines=` row highlight is for citations, and for an outdated thread's jump, whose excerpt fallback reads it. The list follows the review as it reloads, whether or not a file is open.
- **Message text.** Rendered as a markdown subset, the same in the Threads tab and inline in the diff:
  - **Supported:** paragraphs, ATX headings (`#`–`######`, all shown at body size), `*em*`/`_em_`, `**strong**`, `~~del~~`, inline code, fenced code blocks (scroll sideways inside the card), bullet and numbered lists (nesting, start number), blockquotes, pipe tables with alignment, `---` rules, `[label](url)` and `<scheme:…>` links.
  - **Line breaks:** a single newline inside a paragraph is a line break (GitHub-comment style).
  - **Citations:** `path#L10-L20` becomes an in-app link that opens the file with the lines highlighted (a cited file outside the diff opens a read-only excerpt), in text, inside inline code, and as `[label](path#L10-L20)`. A citation is one token: `_`/`*` inside it are never emphasis. Not linked inside fenced blocks.
  - **External links:** `http(s)` and `mailto` links, and bare `http(s)` URLs, open in a new tab. A bare URL ends at whitespace, `<`, `>`, `"`, a backtick, `[`, `]`, or a `)` it did not open; trailing punctuation is not part of it. Any other target (relative, `#…`, `//host`, `javascript:`, `data:`…) shows its label as text.
  - **Shown as text:** raw HTML (including `<!-- … -->`). Images show as a link labelled by their alt text; nothing loads.
  - **Unsupported:** indented code blocks, setext headings, reference links, GFM task lists (`- [ ] x` shows a literal `[ ]`).
- **History** (range reviews: the pane's History tab). A list of rounds, newest first: "Round n (current) · sha" (the live review, all commits), the current round's commits nested under it ("short subject"; each opens that commit's diff read-only, `commit=`), then each past round ("Round k · sha"). The entry being viewed is marked current; in a comparison none is, and rounds A and B carry "From" / "To" badges. Every pick closes the open file and keeps the History tab. Commits are listed under the current round only, so picking one leaves a past round or a comparison. A failed commits fetch shows its error with Retry.
- **Past round.** Picking a past round (`round=` in the URL) leaves the commit filter and shows that round read-only (see [Past rounds](#rounds-and-refresh)):
  - a banner "Viewing round k of n — read-only…" with **Back to current round**; the file header shows a "round k · read-only" badge;
  - no verdict bar, no Accept file, no line selection, no composer, no reply box, no resolve controls; context expansion and cited excerpts read that round;
  - no review-level writes either: no Submit round or Re-send, no Refresh, no Reopen, no recipient picker (the recipient is shown as text), and the actions menu holds only Open agent (absent without a bridge and a recipient). The commit-filter view keeps them;
  - thread cards say how many later replies are hidden;
  - a refused round view shows the refusal in the Files tab; History stays reachable.
  - `round=` naming the current round (or a later one) is dropped from the URL.
- **Compare rounds** (button at the top of History, with two or more rounds) opens a comparison of the previous and the current round (`compare=A..B`; see [Comparing rounds](#rounds-and-refresh)), closing the open file, the round view and the commit filter:
  - **From** and **To** selects replace the button ("Round k · sha", the current round marked "(current)"); From lists rounds before To, To rounds after From; changing either closes the open file;
  - a banner "Comparing round A with round B — read-only…" with **Exit comparison**; the file header shows a "round A → B · read-only" badge;
  - read-only exactly like a past round (no verdicts, selection, composer, replies, resolve controls or review-level writes); still live: the file tree, file navigation, the split/inline toggle, resolved-thread collapse, context expansion (read from round B's head, round A's for a file deleted in the comparison), Focus and thread links, cited excerpts (`side=old` reads round A's head, `new` round B's). Focus marks nothing read;
  - thread filter: This file (each thread once), All (every compared thread once, placed or not, with its note; the badge counts them), Not in diff (with the reason); no Outdated tab. Until the comparison loads every tab shows a loading state; a comparison that failed to load shows its error with Retry in every tab, and in the file pane (a failed reload keeps the loaded lists);
  - a citation link in a message leaves the comparison for the round view of the round that message was written in (`round=<its round>`), since that is the code it cites; outside comparisons citation links keep the current view;
  - no entry point with one round or on commit/uncommitted reviews.
- **Rounds.** A range review whose HEAD moved shows "HEAD moved — Refresh available"; uncommitted reviews have a Refresh button; commit reviews have none. A refresh reports hunks kept/reset/new and threads moved/drifted/outdated/dropped (and, when it carried or dropped groups, "groups K kept, D dropped"), or "No changes; still round n".
- **Closed and gone.** A closed review disables every write and offers Reopen. A removed checkout shows a banner; an unreadable snapshot replaces the tree with the refusal text.
- **Live updates.** Review events refetch what is on screen; uncommitted reviews also refetch on window focus (at most once per 5 s) and every 15 s while the page is visible. A hidden tab refetches nothing until it is visible again. Lists, the review and its file diffs show cached data at once on a revisit and refresh it in the background when older than 30 s. Only verdicts (per hunk, Accept file, and a group's own control) update before the server answers, and revert with a toast if refused; a group verdict changes its hunks only when the response lists them.
- **Unread.** Badges come from the server. Focusing a thread (Focus button, `thread=` link, "Next unread") marks it read; "Mark all read" in the header actions menu clears the whole review, including the "new" badge.
- **Dropped threads.** An uncommitted thread whose lines changed is deleted by the backend. The UI keeps its last fetched copy for the current page session only, in the Dropped tab and as a one-line notice, labelled "dropped: its lines changed". A reload forgets them; replying to one is refused `THREAD_DROPPED`.
- **Submitting.** "Submit round" (range, commit) or "Request review" (uncommitted) opens the recap (see Submitting a round); its primary button composes the prompt. Embedded in cc, it is sent through the cc bridge: success is recorded and toasts "Sent to …"; a bridge failure is recorded with its code and shown with Retry (same submission), Open agent, Copy prompt and Mark as sent. If cc does not answer within the deadline nothing is recorded and the dialog warns that the prompt may already have arrived, so Retry could deliver it twice. A code the UI does not know is shown raw and not recorded. Standalone, the dialog shows the prompt with Copy and Mark as sent; Close leaves it pending. If the prompt was sent but recording its result fails (network error, 5xx), the dialog state resets and the review refetches, so the submission shows up as pending and the header offers "Re-send"; the failure is toasted. The pending-submission banner is hidden while this page is still delivering that submission (a Guide me send in flight). A submission left failed or pending is offered again as "Re-send" in the header. A failed one (the bridge reported an error) reads "Last submission failed (code)". A pending one reads "Last submission isn't recorded as delivered" and warns that it may already have reached the session, so re-sending could deliver it twice: its delivery is unknown after a reload, after a closed copy dialog, or when recording the result failed. With no recipient the recipient picker opens. **Guide me** (the Guided tab) composes a guide prompt and uses the same delivery, dialog (titled "Guide me"), Retry and standalone Copy / Mark as sent; a left-over one reads "Last Guide me request failed (code)" or "Last Guide me request isn’t recorded as delivered" in the header.
- **Session following.** Embedded, a session change with no review open lands the new session as [Opening the page](#review-ui) describes: its one open review, else its checkout, keeping the current tab (the inbox stays the inbox). A conductor session, or one in a project cc does not list, still opens its own single review but otherwise leaves the view alone.
  - **While a review or the New review dialog is open, session changes are ignored, not deferred:** it stays open, and leaving it lands on its own checkout, not the session's. Following resumes with the next session change.
  - A landing that resolves after you navigated yourself is dropped.
  - "Open agent" focuses the recipient session. Standalone, none of this runs.
- **Active-session defaults.** Embedded with an active session, the sidebar's project select opens with an "Active session" group (the session's project and every project its workers are in or were spawned into; same rule as cc's conductor chips), then "Other projects"; the worktree select does the same within the project ("Main checkout" joins the top group when the session or a worker is, or was, on it), then "Other worktrees". Flat without a bridge, an active session, matching projects, or when the lookup fails. The groups refresh when the active session changes, not when a worker is spawned. New review starts with Recipient set to the active session (if live) and Title set to its label, cc's sidebar label (blank if it has none); a field the user edits, Default included, is never overwritten while the dialog is open.
