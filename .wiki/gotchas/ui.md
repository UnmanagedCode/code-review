# UI gotchas

- **The selection clamps at a collapsed gap.** `extendSelection` stops before a gap row; once the gap is expanded the range may span both hunks (the backend accepts it). `frontend/src/lib/selection.ts`.
- **Render nothing under the selection while dragging.** Inserting the toolbar or composer under the first row shifts the rows below it, so the pointer ends up over it and the drag never extends. A mouse/pen release opens the composer directly; touch and keyboard get the toolbar, since a focused composer would pop the soft keyboard and end a tap-to-extend.
- **`pointercancel` must disarm the gutter press.** The armed flag (`dragging` in `useLineSelection`) otherwise survives a cancel, and the next unrelated pointerup anywhere opens a composer. A cancelled press keeps its selection and shows the toolbar.
- **The resolve controls sit inside the reply `<form>`, so they stay `type="button"`.** A default button submits the form and posts the draft. `ResolveControls`, rendered through `ReplyBox`'s `actions`.
- **The SSE echo of our own write is ignored.** Write responses carry the review summary; `applyReview` raises `knownRev`, so the following event has `rev <= knownRev` and triggers no refetch. Anything that bypasses `applyReview` causes one redundant refetch (harmless).
- **Verdicts are the only optimistic write** (per hunk and Accept file). Everything else waits for the server; a refused verdict reverts and toasts.
- **Accept file sends the hunk ids the UI shows as pending, never just the path.** A path alone would let the server accept hunks added by a refresh the UI hasn't loaded, or flip a reject another tab set. The server also skips any hunk that already has a verdict. A refused Accept file reverts its hunks to pending and always reloads, since the revert can clobber a per-hunk verdict set while it was in flight. `acceptFile` in `src/reviews.js`, `FileVerdict` in `frontend/src/features/diff/FileVerdict.tsx`.
- **The active verdict's tint is keyed on `aria-pressed`, not on the button variant,** so it cannot drift from the accessible state. Each verdict's active segment carries its own hue (`success` / `destructive` / `info` tokens) in the background only; the label stays `text-foreground`, because a hued label on its own tint misses WCAG AA 4.5:1 in both themes. Unpressed segments are neutral. The diff view toggle keeps the primary (coral/orange) tint. Ghost's dark hover rule out-specifies a plain `aria-pressed:` background (the `dark` variant adds `:is(.dark *)`), so a pressed segment needs its own `dark:aria-pressed:hover:bg-*` or dark hover washes the tint out: that class is the only hover one required. The light `aria-pressed:hover:bg-*` shade is an affordance, and no hover text class is needed, since the base `aria-pressed:text-*` already beats ghost's `hover:text-accent-foreground`. Classes: `SEGMENT_SHAPE` / `SEGMENT` in `frontend/src/features/common/segment.ts` (the view toggle uses `SEGMENT`); per-verdict `tint` in `VERDICTS` (`frontend/src/features/diff/HunkBar.tsx`).
- **A bridge timeout or an unknown bridge code posts no result.** The prompt may have been delivered, and the backend refuses codes outside its list. The timed-out dialog's Retry warns that it could deliver twice.
- **Citations are linked from the route serialiser, never from the raw text.** Paths starting with `/` or containing `..` stay text. Parsing: [markdown.md](markdown.md).
- **The route wins on load.** A checkout named by the URL beats cc's active session, which beats the stored last checkout; only later session changes switch the checkout.
- **Session following ignores session changes while a review is open, and keeps `view=inbox`** (`useFollowSession`). The effect returns before navigating when `route.review` is set, but still marks the session consumed. The route is deliberately not in the effect's deps, so leaving the review does not replay the dropped change: "← Reviews" lands on the review's own checkout. Adding the route to the deps would turn "ignored" into "deferred". Every follow navigation replaces the whole route, so it re-adds `view: 'inbox'` itself; without that a session change would close the inbox.
- **Spread `REVIEW_SCOPED` (`frontend/src/lib/route.ts`) into every patch that opens, leaves or deletes a review.** `navigate`/`RouteLink` merge into the current route, so a key left out (it was `round`) carries one review's view into the next: leaving a round view of A and opening B landed in B's read-only round view. A new review-scoped route key goes into `REVIEW_SCOPED`, nowhere else.
- **A past-round view hides review-level writes too** (Submit/Re-send, Refresh, Close/Reopen, Mark all read, Delete, recipient picker): they act on the current round, whatever the banner says. The commit-filter view keeps them.
- **A past-round view is a route, not state:** `round=` (range reviews only) puts `round` in the review context and makes it `readOnly`. It loses to `commit=` (History lists commits under the current round only, so picking one clears `round` and `compare`, and picking a round clears `commit`), and `ReviewView` replaces a `round=` naming the current round or a later one out of the URL. Until the review loads, the open file's fetch is held: without the current round number a `round=` URL could fetch the live diff first.
- **`compare=A..B` beats `round=` and loses to `commit=`.** `ReviewView` replaces `round=` out of the URL while a valid comparison is present, and replaces a `compare=` the review cannot have (not a range review, `A ≥ B`, `B` past the current round). Like `round=`, it holds the open file's fetch until the review loads. Details: [round-compare.md](round-compare.md).
- **Write and verdict gates check `pastView`, not `round !== undefined`.** `pastView` is a round view or a comparison; `round` alone keys only the round banner and round-specific text. A new write control gates on `pastView` (or `readOnly`), or it shows in a comparison.
- **Read-only rows have no `data-cell`.** Gutter cells carry it only when selection is enabled, so harness checks in a read-only view (closed, commit filter, past round) match rows by their cell text instead.
- **Uncommitted reviews need polling.** Working-tree edits emit no event, so the page refetches on focus and an interval; threads that vanish become session-local tombstones.
- **The file header's path keeps a flex-basis.** With only `min-w-0 flex-1` it shrinks to "a…" in the narrow desktop middle pane and the header's `flex-wrap` never kicks in; the basis makes the controls wrap instead. `FileHeader` in `frontend/src/features/diff/FileDiff.tsx`.
- **The review list scrolls inside `ReviewList`, not in its column.** In both layouts the column (`DesktopLayout`'s aside, `PhoneLayout`'s main in `frontend/src/features/layout/layouts.tsx`) has `ReviewList`'s section as its last `min-h-0 flex-1` child, so the section's inner `min-h-0 flex-1 overflow-y-auto` div is the scroller. The New review footer is a `shrink-0` sibling after that div, so it stays at the column's bottom edge whatever the list length; anything placed inside the scroller would move with the list.
- **Split pairing keeps each side's line order, so selection runs on the flat rows in both views.** `splitRows` (`frontend/src/lib/splitRows.ts`) only regroups the visible rows; `useLineSelection`, `extendSelection` and ←/→ never see pairs. A new view that reorders lines would break that.
- **Split wraps, inline scrolls.** Split columns can't scroll sideways independently without JS-synced scroll and losing row alignment, so split text cells use `whitespace-pre-wrap wrap-anywhere` and split rowgroups drop `overflow-x-auto`.
- **The split fallback observes `FileDiff`'s root, never the grid or a row, and still needs two guards against flipping.** The root's width is the pane's, but the pane is `main`'s scroll area: split wraps lines and changes the content height, so a scrollbar could appear or vanish and move the width across `SPLIT_MIN_PX` (split → scrollbar → inline → no scrollbar → split…). `DesktopLayout`'s `main` has `[scrollbar-gutter:stable]`, and `useDiffView` leaves split only below `SPLIT_MIN_PX − SPLIT_EXIT_SLACK_PX`. Only the "roomy" boolean is state, so a side-pane drag re-renders the diff only at a crossing.
- **Collapse is adjusted during render, not in an effect** (`useCollapse`). An effect commits one frame with a just-accepted hunk collapsed, which unmounts a Composer under it (the draft survives in the store, but focus is lost).
- **`keepOpen` reads the previous render's selection through `selRef`** (`FileDiff`): collapse must be known before `useLineSelection` gets the visible rows. That is correct only because a settle (a verdict change) never changes the selection in the same render. On a file (re)load nothing consults `keepOpen`: what is settled then starts collapsed.
- **The routed thread is `pinned`, not `forced`** (`useCollapse`). Forced items never collapse; a pinned item is shown until a settle transition happens while it is pinned, which releases it (collapsed, toggleable, takes `open` overrides). A route change or file (re)load pins it again, so navigating to an already-resolved thread shows it open. Hunks holding its range stay forced.
- **Unsent text lives in `state/drafts.ts`, not in form state.** A form remounts whenever its parent changes: a thread card moves from under its line row to under the hunk summary when the hunk is accepted (here, from another tab or an agent, via a refetch), and a split/inline flip re-keys the row a Composer sits under. A `key` can't keep a component across parents, so `ReplyBox` keys its draft by review + thread id and `Composer` by review + anchor; sending clears it, Cancel discards a new comment's. Resolved cards are additionally `hidden`, not unmounted, when collapsed (`SettledThread`).
- **A thread's range is marked by a gutter rail, never a row background.** `cn` is `twMerge`, so a second `bg-*` on a row *replaces* the add/del tint rather than stacking (split picks one tint per half, same effect): that is how the `lines=` wash turned a range over +/− lines into one pale wash. Rails are absolutely positioned bars inside the gutter cell (`Rails` in `frontend/src/features/diff/Gutter.tsx`), so they combine with add/del, target and selection. `rangeMarks` (`frontend/src/lib/ranges.ts`) is the one place that decides what is marked; lanes come from the file's whole thread list, never the visible rows, so expanding a gap never moves a rail. Outdated threads are never in `file.threads` (`rangeMarks` also skips them). Navigation to a live thread (location link, Next unread, Focus on another file's thread; `at` in `ThreadCard`) sets `thread=` and clears `lines=`. `lines=` is for citations, and for an outdated thread's jump: `CitedExcerpt` reads it when the file is not in that comparison. A location link always names its anchor's range (`linkRange` in `ThreadCard`), outdated cards included, though their header shows none: two links in one file must not share an accessible name.
- **Rail colours must reach 3:1 on every background a gutter can carry, tinted ones included.** Light `--primary` (`cc-theme-fallback.css`) passes on a plain row (3.24:1) but fails on the tints: about 2.90 on `success/10`, 2.77 on `destructive/10` and `warning/20`, 2.55 on `info/20`. So the active rail is `bg-accent-foreground` in light and `bg-primary` in dark. `golden.mjs` step 15 measures the shipped rail colours only (`railContrast` composites the cell's translucent ancestor tints on a canvas); it never measures `primary` in light. The rail container has no width: Playwright reports it hidden, so wait for it with `state: 'attached'`.
- **A rail is a background on an empty span, so forced colours (Windows High Contrast) would paint it as Canvas and hide it.** The bars carry `forced-color-adjust-none` and take system colours there (`CanvasText`, `Highlight` when active), as `!important` utilities: with the UA correction off, `dark:bg-primary` (`:is(.dark *)`, higher specificity) would otherwise win in a dark High Contrast theme. High Contrast White's `Highlight` is a dark navy beside black `CanvasText`, so the focused bar is also twice as wide there, with lanes spaced to keep a gap. Step 15's forced pass compares each rail with the system colours read from a sentinel element, in both schemes. Any new mark drawn as a background needs the same.
- **The resolved summary wraps by container query, not by flex basis** (`SettledThread`). Below a 26rem container (`@max-[26rem]`) its range and badges drop under the preview; a plain `flex-wrap` with a preview basis big enough for a phone also wrapped a narrow desktop diff's summary that fits on one line. The threshold sits above a 412px phone (container ≈ viewport − `belowRow`'s `px-3` − scrollbar, about 388px; `@sm`'s 24rem missed it) and below the summary beside a widened side pane; golden step 9 checks 390px and 412px, step 10 the one-line summary with the pane dragged 200px wider at 1100px.
- **No "Collapse hunk" while the selection touches the hunk** (`FileDiff`): collapsing over it would leave a selection that is hidden and inert.
- **The side pane's width is clamped on render, never written back** (`useResizablePane`): a narrower window narrows the pane and widening it restores the stored width. A cancelled handle drag reverts and stores nothing (the same disarm rule as the gutter). The handle is on the pane's right edge, so → and a rightward drag widen it.
- **The pane tab is `view=`, written with `replace`; every other navigation merges and so keeps it.** That is how a thread's Focus or location link (even into a comparison) leaves the pane on Threads, and how a phone's Back (`LEAVE_FILE`) lands on the tab it left. Never put `view: undefined` in a file or thread link: it would own the tab. `REVIEW_SCOPED` clears it, so a newly opened review starts on Files.
- **The list pane force-mounts only its Checkout panel** (`ListPane`): Checkout keeps `ReviewList`'s scope and status selects across a tab switch; the Inbox panel mounts only while active, so the inbox never fetches (or refetches on every SSE event) while hidden. Each panel is `flex min-h-0 flex-1 flex-col`, which keeps the review list's inner scroller and fixed footer working. A hidden panel's content is still in the DOM: RTL `getByText` finds it, so check `closest('[hidden]')`.
- **Inactive pane tabpanels are force-mounted with `hidden`** (`ReviewPane`). `ThreadPanel`'s filter, status and owner state survive tab switches, and the hidden duplicates of thread cards (the diff has its own) stay out of RTL role queries and the accessibility tree. With `forceMount` Radix's own `hidden` is always false, so `ReviewPane` passes `hidden` itself; it wins because Radix spreads the props after its own. Playwright's `getByRole` skips them too, but `getByLabel`/`getByText` counts do not.
- **A focused unread thread asks to be marked read once per card, so the write is deduped, per visit** (`state/readMarks.ts`). Two cards show it on a wide layout (inline and in the hidden Threads tab). The mark is keyed by review, thread and the review `version`, which is `useFetch`'s per-mount load counter: it restarts at 0 on every visit, so `ReviewProvider` forgets a review's marks on unmount or review switch. Keying on `review.rev` would not work, because the mark's own response advances it while the diff still shows the thread unread.
- **happy-dom has no layout.** The side pane → diff pane → split fallback link is proven only in `golden.mjs`; the unit tests pin each half (`installResizeObserver` delivers widths by hand). Row geometry, drag across real rows, sticky headers and overflow are checked in the Playwright harness, not in unit tests. A UI change that moves elements under the pointer is only caught there.
- **RTL `waitFor` hangs under vitest fake timers;** use `vi.waitFor`. `userEvent.setup()` replaces `navigator.clipboard`, so spy on it after `setup()`.
- **Rebuild `frontend/dist` (`npm run prepare`) before running the harness;** the server serves the built bundle.
- **An outdated thread's place is `compare=R..R+1`, R = `anchor.round`** (`at` in `ThreadCard`): its anchor stays the last located one, and it went outdated in the next round. The patch also clears `commit` (it beats `compare`) and `round`. A base-side anchor is never placed in a comparison, so it opens round view R. Its card unmounts on the jump, so `jump` marks it read itself. If the file is not in `R..R+1` (unchanged, or renamed) `FileDiff` falls back to the `CitedExcerpt` of round R. `ThreadCard`'s `unplaced` prop (set from the comparison panel's `reason`) makes Focus skip the jump: in a comparison `side: 'old'` means round A's head, never the base. Cross-file Focus needs no scroll sequencing: the new file's card mounts focused and scrolls itself, and `FileDiff`'s reveal/limit effects guarantee its row exists.
- **New review's Title and Recipient follow cc's active session until edited** (`touched` ref in `NewReviewDialog`): an edit, including picking Default, pins that field for the dialog's life; the recipient only follows a *live* session because the select lists live sessions only.
- **Pinned selects use `<optgroup>`** (`PinnedOptions`): a named group that cannot be selected and needs no styling; a disabled divider option reads as junk to screen readers. Nothing pinned renders flat.
- **cc steers an open frame with `replaceState` + `popstate`, which can change `review` in place.** `App` keys `ReviewView` by review: without it `useFetch` keeps the previous review's `detail` for one render, so the `stale`/`badCompare` effects judge the new URL's `round=`/`compare=` against the old review's rounds and strip them. Links from MCP results (`src/links.js`) always carry `project`, because a route that names it wins over `useFollowSession`'s first-run checkout switch, which replaces the whole route.
